# Phase 5 Plan: end-to-end encryption

Phases 1-4 shipped the desktop client, phone layout and APK, voice notes, threads, the GIF picker, and (PR #1) authenticated media plus SSO login against a real homeserver. Phase 5 turns on **E2EE** with the engine matrix-js-sdk already ships (`initRustCrypto()`, the Rust core Element uses, compiled to WebAssembly; `@matrix-org/matrix-sdk-crypto-wasm` 18.9.0 is in `node_modules`). We write no cryptography; we wire the engine into our stores and build the screens around it. Scope source: `e2ee-plan.md` (stakeholder-approved). Tickets: docs/archive/PHASE5_TICKETS.md. Criteria and testids: docs/archive/PHASE5_ACCEPTANCE.md. Status: docs/STATUS.md "Phase 5". Handoff: docs/archive/PHASE5_DEMO.md.

## Goals
1. **Read and send in encrypted rooms, side by side with Element**: JC, Charlie and Juanjo can read the 6 encrypted rooms on 704.chat (history included, after unlocking with the recovery key they already have) and send text, images, files and voice notes that Element decrypts.
2. **A session Element trusts**: codec verifies itself against Element or another codec session with the emoji (SAS) dialog, and bootstraps cross-signing for brand-new accounts; Element shows codec as a verified session.
3. **Private by default**: new channels and DMs are encrypted; the lock is visible; nothing in an encrypted room reaches a third party the user did not click on.

## Product decisions
| Topic | Decision |
|---|---|
| Engine | `client.initRustCrypto()` after `createClient`, before `startClient` (Advisor risk 1). `createClient` gets `verificationMethods: ['m.sas.v1']` and `cryptoCallbacks { getSecretStorageKey, cacheSecretStorageKey }` (mandatory: without them restore and setup fail silently). Vite: `optimizeDeps.exclude` for the wasm package. |
| Key store | IndexedDB, `cryptoDatabasePrefix` = `matrix-poc-crypto:<userId>:<deviceId>` (every SSO/password login is a new device; a stale store never collides). **No `storageKey`** in P0: the access token already sits in localStorage, so encrypting the key store with a key kept in the same browser adds no real protection; documented limitation. Logout and token rejection call `stopClient()` then `clearStores()` so the keys are wiped. |
| Verification | SAS emoji only (no QR). Outgoing: "Verify this session" asks the user's other devices (`requestOwnUserVerification`). Incoming: Element or another codec session starts it; a dialog pops up to accept. Device isolation stays the SDK default (share keys with all of the user's devices). |
| Cross-signing bootstrap | Only when the account has **no** cross-signing keys (brand-new account, not the three testers). `bootstrapCrossSigning` first (its UIA can bounce: password dialog locally, `m.login.sso` fallback page in a popup on 704.chat), then `bootstrapSecretStorage({ createSecretStorageKey, setupNewKeyBackup: true })`, then show the recovery key once (Copy + "I saved it"; no forced re-typing, same as Element). Triggered from the banner, never automatically. |
| Recovery | One dialog, "Unlock with your recovery key": accepts the base58 key or a passphrase (`deriveRecoveryKeyFromPassphrase` when the server's key description has a `passphrase` block, else `decodeRecoveryKey`). Unlocking loads the backup key, restores every room key, and loads the cross-signing private keys, so the session also becomes **verified** (Element's "verify with recovery key"). The key is cached for the session only. **After an emoji verification with a session that holds the backup key, that key is handed over on the verified channel and history restores by itself (BUG-17); the dialog is for when no other session is available to verify with.** **Guard**: if secret storage already exists on the account, codec never offers to create a new key (it would orphan the Element one). |
| Undecryptable rows | One placeholder row per `m.room.encrypted` event that failed, with the reason from `event.decryptionFailureReason` (Advisor risk 6): `locked-backup` ("Unlock with your recovery key to read older messages", action), `no-backup` (no backup exists; no action), `restoring` (backup unlocked, keys arriving), `unverified` (sender withheld the key; action "Verify"), `not-joined` (sent before you joined), `unknown` ("Unable to decrypt", the key may still arrive). Rows re-render when the event decrypts later, without reload. |
| Encrypted attachments | The SDK has no attachment crypto; `src/lib/matrix/attachments.ts` implements Element's `matrix-encrypt-attachment` v2 scheme with WebCrypto (AES-256-CTR, SHA-256, JWK key): upload as `application/octet-stream`, send `file: { url, key, iv, hashes, v: 'v2' }` instead of `url` (images, files, voice notes). Reading: fetch with the token, decrypt, `blob:` URL. **No server thumbnails** for encrypted images (the server cannot read them): the full image is downloaded and decrypted when the row is in view. `crypto.subtle` needs a secure context: localhost and the APK (`http://localhost` scheme) work; plain-http LAN dev (`dev:lan` from a phone) does not. |
| Encrypted by default | `createChannel` and `createDm` add `m.room.encryption` (`m.megolm.v1.aes-sha2`) at creation; spaces are never encrypted (Element does the same). Join rules unchanged. A lock in the channel header and `data-encrypted` on room items. There is no client URL-preview code today; the criterion pins that no `/preview_url` request is ever made from an encrypted room. GIFs in encrypted rooms render **click-to-load** (the CDN would otherwise learn who viewed what); the picker still searches Klipy because the user asked for it. |
| Sending | `prepareToEncrypt(room)` when the composer gets focus in an encrypted room, so the first send does not wait for the member load and key claims (Advisor risk 4). Encrypt failures surface as a toast; nothing is ever sent in plaintext to an encrypted room (the SDK refuses). |
| Edits, replies, reactions, threads, redactions | `m.relates_to` is cleartext on the wire, so threads and replies work before decryption; `m.new_content` (edits) is inside the ciphertext and aggregates after decryption. **Reactions are sent in the clear** (`m.reaction`; matrix-js-sdk never encrypts them, Element does the same), so the server can see who reacted with what to which event; known limitation. Redactions are cleartext; "Message deleted" wins over any placeholder. |
| Local test data | The raw-API seed cannot encrypt. `npm run seed` (idempotent, never `seed:reset` this phase) adds `#vault:localhost` (Acme HQ, encrypted, alice/bob/dave, empty). `npm run e2ee:sample` is a **Node** matrix-js-sdk client with `initRustCrypto({ useIndexedDB: false })` that posts encrypted texts and an encrypted image to `#vault` as bob, exports its room keys to `seed/e2ee-keys.json` (merged, not overwritten) and logs its device out (Advisor consult 1). Fresh browser contexts read that history through a dev-only `window.__matrixPoc.security.importRoomKeys(json)` hook or through key backup; never from the seed alone. |
| Tests | Two browser contexts per spec (separate IndexedDB = separate devices), never three; one worker. Password login locally (every `loginAs` is a new device). SSO, Keycloak UIA and real cross-signing against Element are the **manual 704.chat pass** (Wave 15). |
| Phone | The dialogs get bottom-sheet variants and 44 px targets as P1; no phone demo script this phase; APK untouched. |

## Risks and mitigations
| Risk | Impact | Mitigation |
|---|---|---|
| Cross-signing UIA over SSO on 704.chat (`m.login.sso` stage, fallback page + polling) is the least certain piece (Advisor risk 5) | New accounts on 704.chat cannot bootstrap; the three testers are unaffected (they already have cross-signing from Element) | Principal spikes it by hand on 704.chat first (PRIN-20); local tests cover the password UIA; the SSO path is a manual 704.chat checklist item. |
| Testers already have secret storage from Element | A naive "set up" would create a second default key and orphan their Element recovery key | `isSecretStorageReady` / `getKeyBackupInfo` guard: existing SSSS always routes to **Unlock**, never to key creation (AC-E5-5). |
| Confusing undecryptable rows | Users read "no backup" as a bug, or miss the one action that fixes it | Placeholder copy per `decryptionFailureReason`; the two fixable reasons carry the action (`locked-backup` -> Unlock, `unverified` -> Verify); `restoring` shows progress. |
| Late decryption not re-rendering | Rows stay as placeholders until reload | `MatrixEventEvent.Decrypted` is emitted on the client, not the room (Advisor risk 2): the bridge subscribes and refreshes the room and thread snapshots; AC-E2-6 pins "no reload". |
| Encrypted media has no server thumbnails | Big images download in full; a long encrypted timeline could pull many MB | Decrypt only rows in view (IntersectionObserver, like `GifMessage`), size the placeholder from `info.w/h`, cache blob URLs per event, revoke on unmount. |
| `encryptEventIfNeeded` sends plaintext when the room is unknown to the client | A script or an early send could leak plaintext into an encrypted room | `e2ee:sample` waits for Prepared and asserts the wire type is `m.room.encrypted` before exiting; QA's wire check does the same for every send criterion. |
| Seeded encrypted history is unreadable by any device created after it | Tests and the demo see UTDs where they expect text | By design (see Local test data): the key-file import hook or key backup; the demo script uses it deliberately (step 4) and then shows the fix (step 9). |
| Fresh device per test login | bob and alice accumulate dead unverified devices; Element shows warning shields; `/keys/query` grows | `e2ee:sample` logs its device out; QA's `secondContext` logs out at the end of each spec; a `scripts/prune-devices.mjs` (P2) if the device list hurts. |
| First-login time (wasm 5 MB, key upload, `/keys/query`) | AC-SH-2 (10 s) at risk; BUG-4 tail effects | wasm is cached after the first load; `loginAs` keeps its 20 s shell timeout; the loading screen names the stage; measure in Wave 15. |
| `crypto.subtle` unavailable on plain-http LAN | Encrypted media fails on `dev:lan` from a phone browser | Documented; the APK's `http://localhost` scheme is a secure context; docs/MOBILE.md note. |
| Two browser contexts on this machine | Memory, flakes | Two contexts max, one worker, contexts closed in `afterAll`; no full-history paging in the encrypted specs. |
| Edits in encrypted rooms are inside the ciphertext; reactions are not encrypted at all (SDK and Element behaviour) | Edits aggregate only after decryption (a UTD target shows reactions on a placeholder); reaction keys and targets are visible to the server | Accepted and documented (plan decision row, PHASE5_DEMO.md known limits); AC-E2-5 pins the wire behaviour. |
